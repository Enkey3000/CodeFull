# CodeFull Test Plan

**Doc ID:** TP-001 | **Version:** 0.1 draft | **Status:** for QA and security review | **Owner:** QA lead **Upstream:** SRS-001, ARCH-001, SEC-001 | **Downstream:** Test Cases (TC-001), UAT Plan, Release Plan, RTM

## 1. Purpose and Scope

This plan defines how CodeFull quality, security, and performance are proven before each release. It covers the backend services, DAL, realtime hub, Execution Gateway and sandboxes, AI Gateway, web app, and (after MVP) desktop and mobile clients. It does not restate requirements; it tests them by ID.

**In scope:** all MVP and FF requirements in SRS-001, all Must SEC controls in SEC-001, NFR-001..026. **Out of scope for MVP testing:** P2 items (real-money track, Enterprise SSO, public API) except that their feature flags are tested to be off and unreachable.

## 2. Test Strategy

Principles: test by risk first (money, sandbox, tenancy, privacy), automate everything that runs more than twice, test contracts rather than mocks, and keep every test traceable to a requirement ID.

### 2.1 Test levels

| Level | Code | What it proves | Tools | Owner | Runs |
| --- | --- | --- | --- | --- | --- |
| Unit | UT | Domain logic: XP and tiers, streaks, scoring, ties, prize split, entitlement rules | pytest, Go test, Vitest | Developers | Every commit |
| Contract | CT | API matches OpenAPI; SDKs compile; consumers match providers | Spectral, Schemathesis, Pact, openapi diff | Backend | Every PR |
| Integration | IT | Services with real Postgres, Redis, NATS, Temporal | Testcontainers, pytest | Developers + QA | Every PR |
| Database | DB | RLS isolation, ledger permissions, migrations forward and back | pgTAP, Atlas | Platform | Every PR touching db/ |
| Sandbox | SBX | Isolation, limits, determinism, no leakage | custom harness, escape suite | Execution lead | Image or policy change, nightly |
| End to end | E2E | Critical user journeys across UI and backend | Playwright | QA | Every merge to main, nightly full |
| Security (static) | SAST | Code and dependency flaws, secrets, IaC | Semgrep, CodeQL, Trivy, Gitleaks, Checkov | DevOps | Every PR |
| Security (dynamic) | DAST | Runtime web and API flaws | OWASP ZAP, Schemathesis | Security | Nightly on staging |
| Performance | LOAD | Latency, throughput, scale targets | k6 | SRE + QA | Weekly and pre-release |
| Resilience | CHAOS | Graceful degradation, failover | Toxiproxy, chaos tooling | SRE | Pre-release, quarterly |
| AI evaluation | AI | Quota, injection resistance, hints-only mode, quality | eval harness | AI lead | On prompt or model change |
| Accessibility | A11Y | WCAG 2.2 AA | axe, manual screen reader | QA | Every release |
| Compatibility | COMPAT | Browser, OS, device support | Playwright, device cloud | QA | Every release |
| Penetration | PEN | Independent attack | External vendor | Security | Pre-beta, pre-GA, annually |
| Acceptance | UAT | Users confirm value | Manual with scenarios | Product | Pre-beta, pre-GA |

### 2.2 Risk-based emphasis

| Risk area | Why | Extra depth |
| --- | --- | --- |
| Ledger and rewards | Money-like value | Invariant tests, crash and retry tests, reconciliation tests, property-based tests |
| Sandbox | Untrusted code | Escape suite, resource abuse, cross-user leakage, fuzzing the harness |
| Tenancy and privacy | Trust promise | Authorization matrix, RLS tests, payload scanning for anonymous leaks |
| Realtime battles | Fairness | Clock authority, reconnect, scoreboard consistency, spectator privacy |
| AI gateway | Abuse and cost | Injection suite, quota accuracy, challenge-mode evals |

## 3. Test Environments and Data

| Environment | Purpose | Data |
| --- | --- | --- |
| Local / CI | Unit, contract, integration (containers) | Synthetic fixtures |
| Preview (per PR) | Web UI review, smoke E2E | Seeded demo data |
| Staging | Full E2E, DAST, LOAD, CHAOS, UAT, pen test | Production-like volume, anonymized or synthetic only |
| Production | Smoke checks, synthetic monitoring, canary analysis | Real data; no destructive tests |

Test data rules: generated by seeded factories; no production personal data outside production (SEC-080); fixed seeds for determinism; time is controlled through injectable clocks; payment tests use provider sandboxes and test cards only.

## 4. Entry and Exit Criteria

| Gate | Entry | Exit |
| --- | --- | --- |
| Pull request merge | Code complete, tests added | UT, CT, IT, DB, SAST green; no new critical or high findings; coverage not reduced; RTM tags valid |
| Staging promotion | Main branch green | E2E smoke green, migrations dry-run passed, DAST no new high findings |
| Beta release | MVP features complete, UAT plan approved | All Must test cases pass; zero open Sev 1 or Sev 2; pen test criticals and highs closed; LOAD target met; A11Y AA verified |
| GA release | Beta exit and KPI review | Regression green; failover and restore drill done within 90 days; rollback rehearsed; go/no-go signed |
| Hotfix | Defect reproduced by a failing test | Fix verified, targeted regression, canary healthy |

## 7. Security Testing Approach

- Every SEC item has a verification type in SEC-001 (UT, IT, DB, SBX, SAST, DAST, PEN, AI, REV). Security test cases are written for each and tagged with the SEC ID.
- Authorization matrix: every role against every endpoint, including cross-tenant and object-id tampering (SEC-009, 010, 014..017).
- Privacy leak scanning: automated search of all API, WebSocket, search, export, and spectator payloads for identity fields of private entries and discreet questions (SEC-017, 018).
- Sandbox escape suite maintained as code: fork and memory bombs, disk fill, network egress, /proc and kernel probes, symlink and mount tricks, timing and cache side channels, container runtime socket access, metadata endpoint access (SEC-040..050).
- Forged header tests: direct calls to services without a valid gateway signature must fail (SEC-011).
- Webhook abuse: forged, replayed, duplicated, and out-of-order Stripe and PayPal events (SEC-055).
- Penetration test per the Pen Testing Plan; findings feed regression tests.

## 8. Defect Management

| Severity | Definition | Fix target | Release impact |
| --- | --- | --- | --- |
| Sev 1 | Data loss, money or ledger error, sandbox escape, tenant data exposure, outage of a core flow | Immediate, 24 hours | Blocks release; triggers incident process |
| Sev 2 | Major feature broken without workaround, privacy flag bypass, security high | 3 days | Blocks beta and GA |
| Sev 3 | Feature degraded with workaround | Next sprint | May ship with approval |
| Sev 4 | Cosmetic or minor | Backlog | May ship |

Security findings follow SEC-100 SLAs (critical 7 days, high 14, medium 30). Every fixed Sev 1 or Sev 2 gets a regression test before closure.

| Metric | Target |
| --- | --- |

## 12. Risks to Testing

| Risk | Mitigation |
| --- | --- |
| Sandbox and realtime behavior hard to reproduce locally | Containerized harnesses, deterministic clocks, staging parity |
| Provider sandboxes differ from production (Stripe, app stores) | Contract tests plus limited production smoke |
| AI nondeterminism makes tests flaky | Evals with thresholds and fixed prompts; tests assert policies, not exact text |
| Test data realism | Seeded factories modeled on SRS volumes; periodic data shape reviews |
| Load environment cost | Scheduled windows, scale-down automation |

## 13. Traceability

Tests carry requirement IDs through annotations and tags (for example the req marker with FR-LRN-005). The RTM generator reads those tags, OpenAPI x-requirement fields, and SEC verification columns. A requirement without a passing test, or a test without a requirement, fails the weekly traceability check.
